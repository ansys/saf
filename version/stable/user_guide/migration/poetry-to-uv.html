Migrate a Poetry-based solution to UV#

Introduction#

This guide describes how to migrate an existing SAF solution from Poetry to UV. Current SAF solution templates generate UV-based solutions. During the transition period, SAF CLI and desktop installer commands support both UV-managed and Poetry-managed solutions, provided you use versions that support UV. Each solution must use only one dependency manager. Poetry is deprecated for SAF solutions, and support is expected to be discontinued in a future SAF release. Check the SAF release notes for current support and deprecation timelines.

UV must be installed before you can follow the commands in this guide. See the official UV installation instructions for other platforms and installation methods. For example:

# Windows with WinGet
winget install --id=astral-sh.uv -e

# Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

Open a new terminal if needed, then confirm UV is available:

uv --version

Before migrating, use SAF CLI version 4.5.0 or later, which supports UV. Check the CLI version with:

saf --version

If you also build desktop installers for the migrated solution, use SAF desktop installer version 1.20.0 or later. Check the SAF release notes for any updated minimum-version requirements.

Before choosing an automated or manual approach, keep unchanged backups outside the solution root until the migrated solution passes validation. Back up each applicable file:

  • pyproject.toml

  • poetry.lock, if the project has one

  • poetry.toml, if the project has one

You can try either of two third-party tools to automate the conversion. Choose one tool; you do not need to run both. If neither produces a suitable result, use the manual migration steps below. Complete the validation steps at the end of this guide whichever approach you use.

Automated migration#

Option 1: migrate-to-uv#

Try the community-maintained migrate-to-uv first. It supports Poetry and converts project metadata, dependencies, groups, package sources, and other settings. Its source repository contains the code and issue tracker. It is not an Ansys or SAF tool, so review its changes rather than assuming the result is correct for your solution.

The commands below pin migrate-to-uv to version 0.12.0 so the same command does not silently use a newer release if the tool changes. This is the version referenced when this guide was updated, not a permanent recommendation. Before changing the pin, review the project’s documentation and release history, and verify the release’s PyPI provenance.

  1. Work in a branch or copy of your solution.

  2. Install UV as described above, then open a terminal in the solution root.

  3. Preview the changes:

    uvx migrate-to-uv@0.12.0 --package-manager poetry --dry-run

  4. If the preview looks reasonable, run the migration:

    uvx migrate-to-uv@0.12.0 --package-manager poetry

  5. Review the output and the resulting pyproject.toml and uv.lock. Check SAF-specific settings, dependency groups, private package sources, selected build backend, and packaged files. The tool attempts to preserve locked versions when it finds the original lockfile, but verify the result.

If the tool reports an error and aborts, read the reported field or feature. When the message suggests a safe equivalent, correct the source configuration and retry from a clean copy. If locking fails after conversion, restore the original files from your backup and remove any generated uv.lock before rerunning the migration without asking the tool to create the lockfile:

uvx migrate-to-uv@0.12.0 --package-manager poetry --skip-lock

Then review the converted project and generate the lockfile yourself:

uv lock

The documented option is --skip-lock (not --no-lock). If the tool still cannot complete the conversion, leaves an unsuitable result, or reports an issue you cannot resolve confidently, use the manual migration below. Do not use --ignore-errors for a routine migration; it allows a partial migration.

If the tool completes with warnings, review and address each warning before continuing. If locking fails because of a private package index, configure UV index credentials as described in the tool’s private-index instructions. If you selected uv_build and the tool reports unsupported package metadata, try --build-backend hatch only if Hatchling fits your project; otherwise use the manual route.

Option 2: convert-poetry2uv#

As an alternative to migrate-to-uv, convert-poetry2uv converts pyproject.toml but does not create uv.lock. Its GitHub README is its usage documentation; the package is also published on PyPI. Pin the version when running it as a tool. For version 0.3.14, preview the conversion with:

uvx convert-poetry2uv@0.3.14 pyproject.toml -n

This writes a preview to pyproject_temp_uv.toml. Review it, then run the conversion on a clean copy without -n:

uvx convert-poetry2uv@0.3.14 pyproject.toml

The converter saves the original as pyproject.toml.org when it writes the converted file; move that backup outside the solution root. It does not convert the lockfile or remove every Poetry-specific file. Before creating uv.lock, follow Step 3 below to remove poetry.lock and check that no active Poetry metadata remains. Do not rename poetry.lock to uv.lock.

The converter’s README warns that it removes Poetry’s build-system configuration and does not preserve optional dependency-group behavior as-is. Inspect the version constraints carefully as well. Choose and configure a replacement build backend, correct any conversion issues, then run uv lock and the validation steps below. If the preview is not suitable, use the manual migration instead.

If an automated migration succeeds, continue with Steps 4–6 below to verify the environment, update workflows, and complete the migration. If neither automated option produces a suitable result, follow Steps 1–3 of the manual route:

Manual migration#

Follow this section if you are migrating by hand. If an automated option produced a suitable UV configuration, skip Steps 1–3 and continue with Steps 4–6 to validate the migration and update project workflows.

The migration choices in this example are specific to this project:

  • The Poetry [build-system-requirements] table pins Poetry for SAF’s Poetry setup flow. It is not needed for a UV project and is omitted.

  • The Poetry source declares PyPI as the primary source. UV uses PyPI by default, so no index table is needed here.

  • Poetry’s packages entry becomes Hatchling’s wheel package selection. Verify the built wheel includes the package data your solution needs.

  • Poetry’s console script becomes [project.scripts]. The original file has no [tool.poetry.extras] table, so this example has no [project.optional-dependencies] table.

  • The local editable ansys-saf-cli dependency is listed in the tests group and mapped to its path under [tool.uv.sources]. UV dependency groups are not installed unless selected; the path mapping is illustrated in Additional dependency and metadata cases.

  • Poetry allows prereleases for selected ansys-saf-sdk dependencies. UV does not offer a directly equivalent per-dependency setting. If preserving prerelease selection matters, use explicit prerelease constraints or decide whether the broader prerelease = "allow" setting is appropriate.

  • The Codespell skip list is updated from poetry.lock to uv.lock.

Additional dependency and metadata cases#
Local path dependency#

Declare a local package as a dependency, then map its name to a path in [tool.uv.sources]. Paths are relative to the directory containing pyproject.toml. Use develop = true in Poetry and editable = true in UV when the package should be installed in editable mode; omit those options for a regular local install.

Poetry
[tool.poetry.dependencies]
my-local-package = { path = "../my-local-package", develop = true }
UV
[project]
dependencies = [
    "my-local-package",
]

[tool.uv.sources]
my-local-package = { path = "../my-local-package", editable = true }
Private index and package routing#

Keep credentials out of both files. Configure them with an approved credential store or environment mechanism. An explicit index makes the intended source clear for the private package.

Poetry
[[tool.poetry.source]]
name = "private"
url = "https://packages.example.com/simple/"
priority = "explicit"

[tool.poetry.dependencies]
private-lib = { version = "^2.4", source = "private" }
UV
[project]
dependencies = ["private-lib>=2.4,<3.0"]

[[tool.uv.index]]
name = "private"
url = "https://packages.example.com/simple/"
explicit = true

[tool.uv.sources]
private-lib = { index = "private" }
Git and direct URL dependencies#

Preserve the exact Git revision. A direct archive URL belongs in the PEP 508 requirement; verify the URL and artifact integrity policy for your project.

Poetry
[tool.poetry.dependencies]
shared-lib = { git = "https://github.com/example/shared-lib.git", rev = "0123456789abcdef0123456789abcdef01234567" }
wheel-lib = { url = "https://packages.example.com/files/wheel_lib-1.2.3-py3-none-any.whl" }
UV
[project]
dependencies = [
    "shared-lib",
    "wheel-lib @ https://packages.example.com/files/wheel_lib-1.2.3-py3-none-any.whl",
]

[tool.uv.sources]
shared-lib = { git = "https://github.com/example/shared-lib.git", rev = "0123456789abcdef0123456789abcdef01234567" }
Extras and environment markers#

Keep package extras (in brackets after the name) distinct from Poetry optional groups, and preserve each Python or platform marker.

Poetry
[tool.poetry.dependencies]
ansys-saf-sdk = { version = "^0.5.0", extras = ["desktop"], python = ">=3.11,<3.13" }
windows-only = { version = "^2.0", markers = "sys_platform == 'win32'" }
UV
[project]
dependencies = [
    "ansys-saf-sdk[desktop]>=0.5.0,<0.6.0; python_version >= '3.11' and python_version < '3.13'",
    "windows-only>=2.0,<3.0; sys_platform == 'win32'",
]
Published optional features#

Use [project.optional-dependencies] for published extras. This is different from [dependency-groups], which is for development and workflow dependencies.

Poetry
[tool.poetry.dependencies]
reports-lib = { version = "^2.0", optional = true }

[tool.poetry.extras]
reports = ["reports-lib"]
UV
[project.optional-dependencies]
reports = [
    "reports-lib>=2.0,<3.0",
]

The dependency constraints in the complete example illustrate equivalent ranges for the source project’s Poetry caret constraints. Verify version ranges, markers, source routing, resolved versions, and group selection for your own solution.

Step 1: Prepare the migration#

Before editing the project, inventory:

  • Runtime dependencies and all Poetry dependency groups, including which groups SAF installs by default and which are selected explicitly.

  • Python version constraints, extras, platform markers, and environment-specific dependencies.

  • Package sources, private indexes, Git dependencies and revisions, local paths, and editable dependencies.

  • Build configuration, package discovery and data files, and commands in CI, scripts, containers, and developer documentation.

Do not assume that generating a UV lockfile preserves the exact versions in poetry.lock. Review the resolved versions and dependency sources, and run your solution’s tests after migration.

Step 2: Translate project metadata#

Update pyproject.toml to use standard project metadata and UV configuration. TOML does not require tables to appear in a particular order, but a readable UV project commonly puts them in this order: [build-system], [project], [dependency-groups], then [tool.uv] and any build-backend-specific settings. uv.lock is a separate file beside pyproject.toml. Use this order as a guide while translating the Poetry project:

  1. Replace the Poetry build backend in [build-system] with a suitable non-Poetry build backend; see Build system and package contents.

  2. Map project metadata and runtime dependencies to [project]; see Project metadata and version constraints.

  3. Map Poetry dependency groups to [dependency-groups]; see Dependency groups and extras.

  4. Add UV-specific settings and package sources in [tool.uv] as needed; see UV configuration.

  5. Generate uv.lock after completing the metadata and source mappings; see Step 3.

For complete before-and-after examples, see Examples.

Build system and package contents#

Important

UV is a dependency manager and project tool. It is not a Python build backend. If your pyproject.toml uses Poetry’s build backend, poetry.core.masonry.api, replace it with a suitable non-Poetry build backend as part of the migration.

Replace Poetry’s build backend with a suitable non-Poetry build backend, and move package discovery and data-file rules to that build backend’s configuration. The complete example uses Hatchling to illustrate one possible choice; select a backend that fits how your solution is packaged. The Python Packaging User Guide’s build-backend recommendations and the build backend documentation are good places to compare options.

Examples include:

Example Python build backends#

Build backend

May fit when

Documentation and considerations

setuptools

You need broad packaging features, including custom discovery or native extension modules.

Review its package discovery, data-file, and extension-module settings.

Hatchling

You need configurable build targets and file selection.

Check its file inclusion rules against the files your solution needs.

These are examples, not interchangeable drop-in replacements. Choose based on your package layout, dynamic metadata, data files, and any compiled extensions. Do not build the distribution yet: finish translating the remaining metadata and make the solution UV-only first.

Project metadata and version constraints#

The standard [project] table uses metadata fields defined by PEP 621. Preserve the fields present in your Poetry project and translate their meaning, not just their spelling. See the PEP 621 specification for the complete metadata format.

Important

Poetry’s caret syntax (^), such as ^1.0, is not valid in UV’s standard [project.dependencies] entries. UV uses PEP 508 version specifiers, so translate the constraint into explicit bounds instead of copying the caret expression.

The table covers common Poetry range forms. UV project dependencies use PEP 508 version specifiers (which follow PEP 440); Poetry’s ^ and ~ operators must be translated. Wildcard ranges can be written as explicit bounds, or as PEP 440 wildcards where supported. Existing PEP-style comparisons can usually be kept.

Dependency groups and extras#

Use [dependency-groups] for dependencies needed by development or specific SAF workflows. A group is a named list of requirements; it is not automatically installed just because it appears in the file. Direct UV commands include the dev group by default; tool.uv.default-groups can change that selection, and other groups can be requested explicitly. SAF CLI applies its own group selection. The main requirements in project.dependencies are installed with the project.

For example:

[dependency-groups]
desktop = ["ansys-saf-sdk[desktop]>=0.4,<1"]
ui = ["dash>=3,<4"]
doc = ["sphinx>=8,<9"]
tests = ["pytest>=9,<10"]

SAF group selection is controlled by the SAF CLI, not solely by UV’s default-groups setting. With a CLI version that supports this option, a command such as saf install <solution> --dependencies ui,tests requests the named groups; if omitted, the CLI uses that version’s default selection. Check saf install --help for the defaults and syntax supported by the installed CLI. Direct UV commands select groups separately, for example:

uv sync --locked --no-default-groups --group ui --group tests

Run this after creating uv.lock in Step 3; Step 4 covers the clean environment install and validation.

By contrast, [project.optional-dependencies] defines package extras. These are part of the package’s published metadata and are selected by consumers installing the package with an extra. Use extras for optional features of the package API; use dependency groups for local development or SAF environment workflows. A Poetry optional group is not automatically a package extra, and changing its table name alone can change how it is installed. See PEP 735 for the dependency-group format and the UV dependency groups guide for how UV installs them.

Poetry dependency options#

Poetry dependency tables can include options in addition to a version. In UV, most dependency requirements are strings using the standard PEP 508 format: the package name, optional extras, version specifier, and optional environment marker.

Translating Poetry dependency options#

Poetry option

UV representation

Example or note

version

Add the version specifier to the requirement string

^0.5.0 becomes >=0.5.0,<0.6.0

extras = ["desktop"]

Put extras in brackets immediately after the package name

"ansys-saf-sdk[desktop]>=0.5.0,<0.6.0"

python or markers

Add a PEP 508 environment marker after ;

"pyinstaller>=6.16,<7; python_version < '3.15'"

source, git, or path

Configure the package in [tool.uv.sources] and, when needed, [[tool.uv.index]]

Preserve the selected source, Git revision, and editable/path behavior

allow-prereleases

No per-dependency equivalent in a PEP 508 requirement

UV’s tool.uv.prerelease setting applies to the project; see below

For example, the Poetry dependency below requests the SDK’s desktop extra as part of an optional desktop group:

[tool.poetry.group.desktop]
optional = true

[tool.poetry.group.desktop.dependencies]
ansys-saf-sdk = { version = "^0.5.0", extras = ["desktop"], allow-prereleases = true }

The UV form is a list of requirement strings in the top-level [dependency-groups] table:

[dependency-groups]
desktop = [
    "ansys-saf-sdk[desktop]>=0.5.0,<0.6.0",
]

Here, the desktop key names the dependency group; [desktop] after the package name requests the desktop extra published by ansys-saf-sdk. They have different purposes even though their names happen to match. Quote the entire UV requirement string. For example, "ansys-saf-sdk[desktop]>=0.5.0,<0.6.0" is valid; writing "ansys-saf-sdk"[desktop]>=... is not.

For a main dependency with multiple extras, put all extra names in the same bracket pair:

[project]
dependencies = [
    "ansys-saf-sdk[core-pim,instance-management-all,core-hps]>=0.5.0,<0.6.0",
]

UV configuration: [tool.uv]#

The [tool.uv] table contains UV-specific settings. It is separate from the standard [project] metadata, and most projects need only a few of these settings. Do not copy every possible setting into a solution; add only settings that match its build, dependency, and installation requirements.

Map package sources carefully. Poetry and UV source priorities and per-package routing are not always equivalent. Preserve the intended registry for every dependency, especially private packages. Do not place credentials in pyproject.toml, lockfiles, or command arguments.

Common UV project settings#

Setting

What it controls

Migration guidance

package

Whether UV installs the project itself as a package

Set this only when needed to control package detection. The current SAF solution template sets package = true.

prerelease

How prerelease dependency versions are considered

UV’s default is if-necessary (prefer stable versions and use prereleases when needed). allow and disallow apply to all dependencies; see the explanation below.

default-groups

Groups included by default by direct UV commands such as uv sync

This does not by itself configure which groups saf install selects; SAF may pass its own explicit group selection.

[[tool.uv.index]]

Package index definitions and their priorities

Map Poetry sources deliberately; preserve private-index routing and dependency-confusion protections.

[tool.uv.sources]

Per-package sources such as indexes, Git repositories, and local paths

Use it when a dependency must come from a particular source. Preserve immutable Git revisions and local-path behavior.

constraint-dependencies and override-dependencies

Additional resolver constraints or overrides

These can change resolution across the project. Use only when the project requires them and document why.

Poetry’s allow-prereleases = true applies to an individual dependency. UV’s tool.uv.prerelease setting is project-wide, so setting it to "allow" permits prereleases for every dependency, not just the one that had the Poetry option. UV also supports "disallow" and "explicit"; its default "if-necessary" prefers stable versions and falls back to prereleases when needed. There is no exact per-package switch with the same meaning as Poetry’s option.

If only one package should use a prerelease, include an explicit prerelease version in that package’s constraint only when that is the intended range. For example, "ansys-saf-sdk>=0.5.1rc1,<0.6.0" explicitly admits versions from that release candidate onward. Then inspect uv.lock to confirm the resolver selected the intended version. Do not set prerelease = "allow" globally unless prereleases are acceptable for all project dependencies.

For example, the current SAF solution template uses the following settings:

[tool.uv]
package = true
prerelease = "if-necessary"

This is an example, not a required configuration. Confirm that package installation and prerelease handling match your solution before adopting these values.

Private index credentials should be supplied through an approved external credential mechanism, not stored in project files or source control. For the complete setting list and current syntax, see the UV project settings reference and the UV package indexes guide.

Step 3: Switch the active project to UV and create the lockfile#

Before running SAF commands on the migrated project, make the solution root UV-only. Use the backup made before migration for comparison; do not leave backup files inside the solution.

Important

SAF rejects a solution that contains both Poetry and UV metadata. Do not run saf install or saf build while converting the active project. Finish the metadata and lockfile switch first.

Lockfile layout#

A lockfile records resolved dependency versions and sources. It is generated by its package manager; it is not just a renamed copy of the project configuration.

Before: Poetry
my-solution/
├── pyproject.toml
└── poetry.lock
After: UV
my-solution/
├── pyproject.toml
└── uv.lock

  1. Finish converting pyproject.toml using the mappings in Step 2. Remove active Poetry configuration, including [tool.poetry], the Poetry build backend, and Poetry-only dependency-manager settings. Add the selected non-Poetry build backend and any UV-specific settings the project requires.

  2. Remove poetry.lock from the solution root. Do not rename it to uv.lock; keep the original lockfile only in the backup outside the solution root.

  3. Check that the active project contains UV metadata only: standard [project] metadata, any required [tool.uv] settings, and no [tool.poetry], Poetry build backend, or poetry.lock.

  4. From the solution root, generate a new lockfile with UV:

    uv lock
uv lock --check

Review uv.lock for unexpected version, source, or Git revision changes compared with the saved Poetry lockfile. A successful lock operation does not prove that the old and new environments are equivalent. Resolve unexpected changes before proceeding rather than accepting them without review.

Step 4: Verify the UV environment#

Install the solution and its intended dependency groups in a clean environment. For example:

uv sync --locked --no-default-groups --group ui --group tests

Specify the groups your workflow needs; replace ui and tests with the groups defined by your solution. Run the solution’s unit tests, integration tests, and application smoke tests in that environment. For example, if the project uses pytest:

uv run --locked pytest

Replace pytest with the test command used by your project.

Build the distribution to check the new non-Poetry build backend:

uv build

The resulting wheel and source distribution are written to dist/. Check that they include the modules and non-Python files your solution requires.

Step 5: Update SAF and project workflows#

  1. Replace Poetry commands in context rather than doing a global text substitution. The following common commands are starting points:

    Poetry command

    Common UV equivalent

    poetry install

    uv sync --locked

    poetry install --with ui,tests

    uv sync --locked --no-default-groups --group ui --group tests

    poetry run <command>

    uv run --locked <command>

    poetry lock

    uv lock (then verify with uv lock --check)

    poetry build

    uv build (requires a suitable build backend)

    poetry add <package>

    uv add <package>

    poetry add --group ui <package>

    uv add --group ui <package>

    These are starting points, not exact command substitutions. poetry install --with ui,tests also installs Poetry’s non-optional groups. The UV example suppresses UV’s default groups and adds only ui and tests (in addition to the project’s main dependencies). If Poetry installs other groups by default, add them to the UV command or configure the same UV defaults. Review lock, publish, and source-management commands separately.

  2. If present, update CI, scripts, containers, and onboarding instructions to use the selected UV workflows. Ensure they install the same dependency groups and use the same Python versions as before.

Use SAF CLI and desktop installer versions that support UV. Then install the solution:

saf install <solution-name>

During this installation, SAF reports the detected dependency manager and its version in the input summary. For a UV-managed solution, expect the dependency manager to be reported as uv. This confirms which dependency manager SAF detected for that solution; it does not replace the remaining installation, test, and packaging checks below.

If you specify dependency groups explicitly, use the syntax supported by your installed SAF CLI and select the groups your application requires. Verify that the installed environment works; a successful uv sync by itself does not verify SAF installation or packaging.

For solutions distributed with a desktop installer, also build and test the installer using your normal deployment options:

saf build <solution-name>

If you distribute an offline installer, test that path as well:

saf build <solution-name> --offline-package

Step 6: Complete the migration#

Before considering the migration complete, verify that:

  • A clean environment can be installed from uv.lock without changing it.

  • The expected dependency groups, private sources, local/Git dependencies, and supported Python versions work.

  • Tests and application smoke tests pass.

  • SAF CLI installation and, where applicable, desktop installer packaging and installation work with the migrated solution.

  • CI, scripts, containers, and developer instructions no longer depend on Poetry for this solution.

  • The solution contains no Poetry lockfile or Poetry-specific metadata that could make SAF identify it as a mixed dependency-manager project.

During the transition period, different solutions may use different dependency managers, but each individual solution must use exactly one.
